## Decisions (conservative calls on ambiguous points)

- **S5-01 validation.** The draft is parsed with the create route's own schema (exported `CreateBody`, so the two cannot drift), plus the same date-order check and reference check. With `eventId`, children already linked to that event may stay even if archived since (as the edit route allows); new ones must be active. The demo family is not blocked: nothing is written.
- **S5-01 archived children.** As in `loadPlanInputs`, archived children drop out of the draft; a draft whose children are all archived is left out of the "after" plan rather than becoming a whole-family event.
- **S5-01 what counts as a change.** `perDay` is the plan's `rate` rounded to one decimal, so a row appears when the two rounded values differ or the end moves; a change too small to show as a different number is left out. `end` is the plan's effective `end`.
- **S5-01 ordering.** Relative change is the larger of (change in `rate` / the old `rate`, at least 0.1) and (days the end moves / days from today to the old end). Ties sort by title, child name, then ids.
- **S5-01 asOf and drafts.** Today is the family's today (the app clock). A draft for a new event gets the id `preview`; an edit takes the stored event's id and replaces it (an archived stored event is simply not in the "before" plan).
- **S5-02 when it asks.** Only while the whole form is valid (the same checks Save runs, now one `check()` in the form, so the two cannot disagree). A name is needed, so nothing shows until the event is named and has a day. When the form turns invalid the list disappears. The request goes 400 ms after the last change to anything in the sent body, with `eventId` on an edit; an older answer never replaces a newer one.
- **S5-02 the list.** Under the capacity field, after all the rules: a "What changes" title and plain list, no box or icon. The unit is singular only when the new amount is exactly 1 ("1 lesson a day"). "and N more" counts the rows hidden past 5 plus the server's own `more`. While a new answer loads the old list stays; an error (or a 401/404) clears it and Save is unaffected, as it never waits for the preview.
- **S5-02 changed test helper.** `writes()` in `schedule-fixtures.ts` now leaves out the preview POST, since it only reads; otherwise every existing event-form test would count it as a write. The fake API's allowed body keys gained the preview's (`event`, `eventId`).
- **S5-02 not checked.** 360 px layout is a plain list with wrapping text (jsdom has no layout, so it was not measured).
- **S5-03 holiday shape.** Each holiday is `{ key, start, end, label }` (the ticket asks for `{ start, end, label }` plus a stable key). Keys: `labor-day`, `thanksgiving`, `winter-break`, `mlk-day`, `presidents-day`, `good-friday`, `memorial-day` (`HOLIDAY_KEYS`). Thanksgiving is one entry, Thursday to Friday. Results are in date order.
- **S5-03 "in range".** A holiday is returned when any of its days falls in `[start, end]`, and it is cut to the range, so a template never adds days outside the school year (a winter break running past the last day ends on that day; a range starting on Jan 1 still gets that day of last year's break). Good Friday comes from the Gregorian Easter algorithm in integer arithmetic.
- **S5-03 break runs.** `onOffBreaks` returns one range per run of break weeks (2 weeks off is one 14-day range, first day of the first week to last day of the last), not one per week, because a parent sees it as one break. The range is whole weeks, so it includes the weekend; the last is cut at `end`. A break that would start after `end` is dropped. `weeksOn` below 1 or `weeksOff` below 0 (or not whole) throws `EngineInputError`; `weeksOff` 0 gives none.
- **S5-03 shapes as data.** `CALENDAR_SHAPES`: `36-weeks` (pattern null, holidays only), `sabbath` (6 on, 1 off), `three-terms` (12 on, 2 off), each with a label for the screen.
- **S5-03 no version bump.** Only new exports and no plan number changes, as in S4-08, so `ENGINE_VERSION` stays 0.9.0.
- **S5-04 how.** Same pattern as S3a-03: every item is parsed with the create schema and date-checked first (errors read "Day off N: ..."), then one transaction creates them in order with the single create's own `createOne` (reference check included, so one foreign child id rolls everything back). 201 returns the rows in request order. Body `{ blockedRanges: [...] }`, 1 to 100 items, strict. `kind` defaults to `vacation` per item, as in the single create. Like the single create, it has no demo-family block.
- **S5-05 where the button goes.** `ScheduleList` takes a `panels` list (id, label, render) whose buttons sit beside Add and open in place of the Add buttons, like "Add several" and "Import CSV" (which now go through the same list). A panel is given the loaded rows (`existing`) and `onSaved(created)`.
- **S5-05 the choices.** A "Year shape" select (the three built-ins, then Custom), First and Last day of the year (left blank: the app doesn't store school-year dates and a guessed default would be a policy), and the seven holidays as checkboxes, all ticked. Custom shows Weeks on and Weeks off (whole numbers 1 to 20 each; the defaults 4 and 1 are only starting values). The year may be at most 400 days (as a plan request), which also keeps a template under the bulk limit of 100. `HOLIDAY_LABELS` was added to the engine so the checkboxes name every holiday whatever the dates.
- **S5-05 the preview.** "N breaks to add" and a plain list ("Thanksgiving: Nov 26–27", "Break: Sep 28 – Oct 4"; no year). Pattern breaks are whole weeks (Monday to Sunday for a Monday week start), so they read "Oct 5–11", not "Oct 5–9" as the ticket's example does. Shown only once the dates and weeks are valid; errors show after a tap on Add breaks, and Add does nothing while there is a problem or nothing to add.
- **S5-05 overlaps.** A break that shares a day with an existing day off **for the whole family** is left out and counted as "N already in your days off". A day off for some children only does not cover a family-wide break, so it doesn't hide one. Among the template's own breaks, a holiday lying wholly inside a break week is dropped (the break already covers it); partly overlapping ones are both kept, since days off combine.
- **S5-05 what is sent.** One `POST /api/blocked-ranges/bulk`: label ("Break" for pattern breaks, the holiday's name otherwise), kind `vacation` for pattern breaks and `holiday` for holidays, `childIds: []`. On success the new rows join the list and the panel closes; on an error the message shows and the panel stays open.
- **S5-05 engine change.** `HOLIDAY_LABELS` (and its use inside `usHolidays`) is a small addition to the S5-03 helpers; the labels are unchanged and the S5-03 tests still pass as written. Still no `ENGINE_VERSION` bump.
- **S5-05 not checked.** 360 px layout: the panel reuses the form's `field-row` (two date fields side by side, as the other forms do), the holiday checkboxes and plain lists, all with 44 px targets; jsdom has no layout, so it was not measured.
- **S5-06 migration number.** `012_calendar_template.sql` (the next free number after 011).
- **S5-06 what the database checks.** A name of 1 to 60 characters, `breaks` a JSON array of 1 to 100 entries, a real family (ON DELETE CASCADE). The fields inside each break are checked by the API only (a CHECK over JSON elements would need a function for little gain, as the table is only written by the API). `db/test/validate.sql` and `db/test/calendar-template-migration.test.ts` cover these.
- **S5-06 breaks.** Each break is a strict `{ offsetDays 0-400, lengthDays 1-60, label, kind }`, whole numbers; `kind` is any day-off kind (`BLOCKED_KINDS`, as the ticket says, so a saved `missed` day round-trips). `label` is trimmed, up to 60, and a blank one is stored as null (a day off may have no label, so "Save this year" can keep it).
- **S5-06 API.** GET returns `{ id, name, breaks }` oldest first; POST validates strictly (unknown keys 400) and returns 201 with the saved template; DELETE is 204, or 404 for a malformed id, a missing one or another family's. Names need not be unique. Like days off, templates are not blocked for the demo family.
- **S5-07 which days off are saved.** Those that start from the year's first day up to 365 days after it (so a year is the first day plus the 365 after it), and are for the whole family. Days off for some children only are left out and counted ("2 days off for individual children are left out"). A day off that starts before the first day is not saved even if it runs into the year. Kind and label are kept as they are (a day off with no label stays unlabelled; the preview names it by its kind). A break longer than the 60 days a template stores is cut to 60.
- **S5-07 the form.** "Save as a template" sits beside "Use a template" (another `panels` entry). It asks a name (1 to 60) and the year's first day, says how many days off will be saved, and errors (no name, no date, no whole-family days off in that year, more than 100) show on Save template. After saving it shows "Saved “name”. Find it under Use a template." with Done, because closing at once would give no sign it worked; the days off list is not touched.
- **S5-07 applying.** Saved templates are listed under "Your templates" after the built-in shapes and Custom. A saved one asks only for the new year's first day (no last day, no holidays) and previews every break shifted by days (`first + offsetDays`, length kept), with the same family-wide overlap rule and "N already in your days off" note, then one bulk POST (`childIds: []`, kind and label as saved). A failed load of the saved list just offers none.
- **S5-07 deleting.** "Delete this template" appears when a saved one is chosen and asks first (the same confirm dialog as the lists use: "Days off already added stay as they are."); the choice falls back to 36 weeks.
- **S5-07 not checked.** 360 px layout and the native `<dialog>`'s look, as jsdom has no layout; the panels reuse the forms' existing classes.
- **S5-08 how.** Up to 480 px the three control groups (`tl-edit-moves`, `-dates`, `-ends`) become `display: contents`, so their controls form one non-wrapping row that scrolls sideways (scrollbar hidden), in the DOM order: week moves, Start and End fields, Reset (when changed), end steps, Copy. The markup is unchanged. Above 480 px nothing changed (the 640 px rules are untouched).
- **S5-08 the top row.** Title and "Subject · Child" now sit side by side on one line (title first, the subtitle taking what is left and ellipsised), with the 44 px × beside them, so the bar is two rows, not three. The date fields and their labels are 44 px tall in this layout (40 px on wider screens, as before).
- **S5-08 keeping the selection visible.** No code change: `useKeepAbove` already measures the bar's height and scrolls the selected bar above it, and the bar is now shorter. Measured in Chromium (puppeteer, dev data): the bar is 101 px tall at 360 and 390 px (was about 220 at 700 px), every control 44 px or more, and the selected bar's bottom sits well above the bar's top.
- **S5-08 test.** A web test checks the order and names (Close, Move back, Move forward, Start, End, End a week later, Copy). Sizes are the tester's browser pass and the S5-09 script.
