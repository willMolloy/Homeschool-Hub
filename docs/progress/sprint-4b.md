## Decisions (conservative calls on ambiguous points)

- **S4b-01 ranges.** Over 400 days the first range is the earliest start to start + 399. If the shown week ends after it, a second range ends at the shown week's end, starting at the later of (week end - 399) and the day after the first range (so never over 400 days and never overlapping). A merged plan is the first range's plan (the engine plans the whole assignment; only the returned days are cut) with the other range's days added once each, sorted.
- **S4b-01 what can lose a forecast.** Only an assignment that runs past the requested end (start + 399 days) can lose its forecast, as the ticket says. In the two-range case a plan between the two ranges has a gap in its days; `forecastFinish` copes (it falls back to school days after the last day), so the effect is limited to assignments ending in that gap.
- **S4b-01 changed test.** The S4-09 test "asks for the span ... held to 400 days" (`briefingRange`, one `{from, to}`) is replaced by tests of `briefingRanges` (an array), because the ticket changes what is requested: the start is kept, not the shown week.
- **S4b-02 "this week" and the undo.** The stored record counts as this week's when its `weekdays_from` equals the current week's start. Then `previous_weekdays` is kept and only the current days change; if the new days equal it (any order; null = every school day) both columns are cleared. An older record is replaced as before. The same rule runs in SQL for a subject default change, over each uncustomised started assignment on its own record.
- **S4b-02 changed expectations.** Three S4-01b/S4-03/S4-04 test lines said "a later change overwrites both". They now expect the first change's days to stay (assignment: `null` instead of `[5]`; subject: `[1, 3]` instead of `[5]`), because that is what the ticket changes.
- **S4b-03 no progress.** Measured as `forecastFinish` measures it: the plan's position from the start of the first applied check-in week to the end of the last, with at least 2 distinct applied weeks and work left. It is done in `briefingLines.ts` (no engine change, version unchanged). So a child who stopped after a first week with progress is still not flagged (the report's smaller note); this is the ticket's wording ("no progress across them"). `{n}` is the number of applied check-in weeks (not necessarily consecutive).
- **S4b-03 very late.** More than 26 weeks late (27 or more after rounding) gives the plain wording; exactly 26 keeps the count. One line per assignment, in the late slot, before plan problems.
- **S4b-04 what counts as a tap.** A tap on a day chip (a tap that would remove the last day does nothing and doesn't count). After a tap the S4-07 rule is unchanged: equal to the inherited days sends null, so tapping Monday off and on again on an assignment with its own days equal to the subject's sends null (the parent did touch the chips). Adding is unchanged. "Set as default" also counts as touching (the assignment then follows the subject).
- **S4b-05 the mark.** Kept in the form as the subject and days it was made for. It is shown as "Will be the default for {subject}." with an Undo button. Tapping a day chip or choosing another subject withdraws it (the days it was made for no longer match what is shown); Cancel discards it with the form. The days stored on the subject are the ones chosen when the button was pressed (every school day stores null, as before).
- **S4b-05 Save.** PATCH the subject, then `l.subjectSaved` (lookups follow), then the assignment with `weekdays: null` (on edit it is sent whenever the stored value isn't null, even without a chip tap). If the subject PATCH fails the error shows in the form and nothing else is saved; if it succeeded but the assignment save fails, the subject stays changed, the mark is cleared and the chips follow the new default, so a retry saves null.
- **S4b-05 changed tests.** "Set as default patches the subject, then the assignment saves null" and "choosing every school day ... offers to clear it" in `assignment-weekdays.test.tsx` expected the PATCH on the button; they now expect it on Save (and no request before).
- **S4b-06 how.** One CSS rule for every use of `.day-chip`: the picker grid is `repeat(auto-fit, minmax(44px, 1fr))`, so it wraps to a second line when 44 px chips don't fit, and the missed-day sheet (already a wrapping flex row) gets the same `min-width`. The `--day-count` variable is gone. The Events day picker uses the same component, so it is fixed too.
- **S4b-06 not checked.** jsdom has no layout, so the widths were not measured in a browser; the tester pass should measure 5, 6 and 7 days at 360 px.
- **S4b-07 which day.** Offered days are never after today, so "today if offered, else the latest offered day" is the last offered day. It applies until a day is tapped, and again when a tapped day stops being offered (a change of who), so Save stays enabled whenever any day is offered. Who stays Everyone; a week with no offered days still says "No days to mark." with Save disabled.
- **S4b-07 changed tests.** The S4-10 test that expected Save disabled on opening now expects today selected; "drops a chosen day that stops being offered" now expects the fallback day (Wednesday) selected instead of Save disabled.
