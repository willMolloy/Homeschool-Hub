## Decisions (conservative calls on ambiguous points)

- **S6b-01 what stays.** The table goes; the per-child "Make an adjustment" entry, the "nothing planned" lines and the per-child warnings list stay (the warnings are a separate S6b-14 concern, so they are not touched here). With no table to caption it, the child's name is no longer `aria-hidden`.
- **S6b-01 changed test expectations.** Tests that used `findByRole("table", { name: "Frank" })` as "the plan has loaded" now wait for the "Make an adjustment for Frank" button (`this-week`, `briefing`, `plan-debug`). `this-week`'s "one button per student" no longer expects a table beside the button (it expects none). The old T-03b "parents see only the tables" test is now "parents see no table and none of the debug extras". Table-content tests already used `?debug=1` and are unchanged.
- **S6b-05 the date-only Reset is removed.** It only undid this visit's date moves, and the undo bar (S6-08) now offers Undo after every move and "Reset to original" covers the rest; two Resets confused (the S6 verification said so). `useAssignmentEdit` no longer keeps `originals`, and `EditBar` lost its `original` prop.
- **S6b-05 removed helpers.** `shiftEnd`, `canEndEarlier`, `moveWeeks` and `WEEK_DAYS` (select.ts) are deleted with their buttons; nothing else used them.
- **S6b-05 More.** A disclosure button (`aria-expanded`) opening a small menu upward from the bar. Heavier and Lighter keep it open so they can be tapped twice (S6-10 compounds); Reset to original closes it and opens the existing confirm dialog. Esc closes the menu first, then the bar; a tap outside closes it; picking another bar closes it.
- **S6b-05 phone layout.** Name and close on top, then the two date pickers sharing one row (13px text so both fit at 360 px), then Copy and More: two rows of controls under the title row, measured at 360, 390 and 1280 px in a browser: nothing past the right edge, every control 44 px or more (the date text is 13px, so it is the one small thing). The scrolling row of S5-08 is gone, so S7-09 (already marked not needed) stays dropped. The bar is 153 px tall on phones.
- **S6b-05 changed test expectations.** `timeline-edit-bar.test.tsx`: the unit tests for `shiftEnd`/`canEndEarlier`/`moveWeeks` and the tests "moves the whole assignment a week then Reset", "ends a week later" and "leaves out End a week earlier" are replaced by: the bar has Start, End, Copy and More only; More's menu and Esc/outside behaviour; a changed End picks save the end only. The bar-content assertions (S3a-02, T-08) and the S5-08 order test now expect Close, Copy, More (dates before them). "shows the API's message inline" and the undo-bar tests trigger a move through the End picker instead of "Move forward a week". `timeline-nudge.test.tsx` and `undo-bar.test.tsx` open More before Heavier, Lighter and Reset to original. Nothing was weakened: every behaviour that remains is still asserted.
- **S6b-06 constants.** `SOFT_CAP_KNEE_PX` 56 (a typical day, 20 points) and `MAX_BAR_PX` 96 (was 100, which only the picker preview used), both in `features/plan/scale.ts` as the ticket's starting values. A bar is exact up to 56 px, then 56 + 40 x (1 - e^(-(raw - 56) / 40)): 84 px raw draws about 76, 280 px about 95.9, 840 px (300 pages a day) 96 to the pixel.
- **S6b-06 where it applies.** `bandHeight` (daily and weekly bands, and so `rowHeight`), `smoothColumns` (the raw height before its dead band) and `thicknessToPx` (the picker preview). The All subjects strip normalises to 32 px, under the knee, so the cap leaves it alone. `PX_PER_THICKNESS` is unchanged.
- **S6b-06 changed test expectations.** `thickness-picker.test.tsx`: the "Very heavy" preview was `30 * PX_PER_THICKNESS` (84 px) and is now `softCapPx(...)` (about 76 px) because 84 px is above the knee; the 100-per-page and 100,000-point clamp checks are unchanged (they still reach 96, now `MAX_BAR_PX`). The existing layout tests (all under the knee) are unchanged.
- **S6b-10 final constants.** `LANE_GAP_PX` 2 and `SUBJECT_GAP_PX` 4, the ticket's starting values, kept after one look in Chromium at 360, 390 and 1280 px on the demo family (`screens/sprint-6b/before-*.png`, `after-*.png`; the before is after S6b-06, so only the gaps differ). `LABEL_ROW_PX` stays 16: the name of each lane sits in its own 16 px line between bars, so two lanes' bars are still about 20 px apart (and rows of the same lane 2 px); shrinking that line would crowd the 12 px names, and the ticket asks to keep labels readable. Outside names (T-11d/e) are unchanged and still clear the bar above (tested).
- **S6b-10 tests.** No existing layout expectation changed (they use the constants by name). Added: the constants, every row at least 2 px below the one above (sample family, both widths, every zoom), the first row clear of All subjects, and an outside name clear of the bar above.
- **S6b-10 browser check.** Scratch database `hh_scratch_dev` (reset and seeded), dev servers on 3000 and 5173; both stopped and the database dropped afterwards.
- **S6b-09 which range.** With no plans at all (`plans.length === 0`) the view is the start of today's month through the end of the month ten months later (11 months, week-aligned; from 2026-10-28: 2026-09-28 to 2027-09-05). Plans that exist but have no planned day in the school year (for example everything archived is not in the list, but an assignment dated outside it is) keep the old behaviour, the whole fetched school year, so only a truly empty family gets the new range. The plan is still fetched for the school year (unchanged request).
- **S6b-09 what the empty page shows.** The picture (months, today, days off and events, with the layout code unchanged: zero lanes already worked), the zoom presets and, at This month, the month arrows, then one line "Nothing planned yet." The header's "+ Add assignment" is unchanged. No child filter, edit bar or lanes list (nothing to pick). The "All subjects" label is not drawn when no row is, since its strip is empty; the strip's space stays so the calendar keeps its frame.
- **S6b-09 changed test expectations.** `timeline-view.test.tsx`: "shows only the planned weeks plus today" used `shownRange(fetched, [], ...)` expecting the whole fetched year for no plans; that is now the empty-calendar range (the whole-year case is kept with plans whose days are all empty). "says so when nothing is planned" expected no picture; it now expects the calendar picture, the line and the Add button. New: layout with zero lanes at both widths and every zoom, the zoom presets on the empty page, and adding an assignment from it replaces the line with the new bar.
- **S6b-09 not checked.** The empty calendar was covered by tests only; not looked at in a browser.
- **S6b-07 where and when.** The note sits right under the Unit and Total row (the ticket says "under the total") and uses the form's existing pace (total over the school days of the chosen dates and weekday chips), so it appears only once total, dates and days give a pace and follows every edit of them. The thresholds are strictly-above: 60 pages, 5 chapters, 5 lessons, 240 minutes a day. It is a `role="note"` paragraph, not an alert, and Save is untouched. "Add several" and the timeline sheet: the timeline sheet uses `AssignmentForm`, so it gets the note; Add several has no per-row dates, so it is left alone.
- **S6b-08 the dropdown.** Order: Choose a subject…, the family's subjects, an "Add a common subject" group (the ticket's 14 names minus any the family has, archived ones included, since their name is taken), then New subject…. Choosing a common name posts `{ name, color }` with the next free palette colour (`nextUnusedColor` over active subjects) and selects the result. New subject… opens a "Subject name" field with an Add button (accessible name "Add subject" so it is not confused with the form's own Add); Enter in it adds the subject and does not save the assignment form around it. The field's limit is 60 characters (the API's).
- **S6b-08 duplicates.** A 409 selects the existing subject (matched ignoring case) and closes the field. If the existing one is archived it is not in the list, so the form says "Math is archived. Unarchive it under Subjects." rather than selecting something invisible. Any other failure: "Couldn't add that subject. Please try again.", name kept.
- **S6b-08 lookups.** `Lookups.subjectSaved` (S4-07) now also appends a subject it has not seen, in both `WithLookups` and the timeline's `applySubject`, so a created subject appears at once in the list, in the weekday defaults and in the form's hints. No new member.
- **S6b-08 Add several** gets the same select (the same component). "No subjects yet. Add them under Subjects." is gone.
- **S6b-08 Subjects screen.** "No subjects yet." stays and, under it, an "Add common subjects" group of 44 px chips (the 14 names). A tap posts the subject and adds it to the list. The group is kept (minus what was added) for the rest of the visit when the family arrived with none, so a parent can tap Math, Reading, Science in a row; a family that already has subjects never sees it. Kids have none (`RosterPage` takes an optional `suggestions`).
- **S6b-08 changed test expectations.** `subjects-add.test.tsx`: two tests waited for `findByText("Art")` on an empty family; the new "Art" chip satisfied it before the POST finished (and then left the page), so they now look for "Art" inside the Subjects list. Nothing else changed; no test asserted the old "No subjects yet" hint on the form.
- **S6b-08 not checked.** Tests only; not looked at in a browser (the 360 px chips wrap with `flex-wrap`).
