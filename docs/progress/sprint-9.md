## Decisions

- **S9-01 Records is a placeholder** ("Records — coming soon") until the later Records tickets.
- **S9-01 Track work code stays, unlinked.** `routes/TrackPage.tsx`, `features/track/` and the check-in hooks are untouched but nothing routes to them: `/track` (with its query) redirects to `/schedule?view=week`. A finished week can still be checked in from Schedule · Week by stepping back a week (that board is the same component). Its tests render the page directly (`renderTrack` in `test/render.tsx`).
- **S9-01 the unanswered-check-in nudge** on Schedule · Week ("Last week isn't checked in yet.") stays for now and links to `/schedule?view=week` (it used to link to `/track`). Home never showed it (Briefing `showNudge={false}`) and still does not.
- **S9-01 Home** has two equal cards, Schedule (unchanged content) and Records ("Attendance, hours and books"; no totals until Records exists). The Track work card, and with it its "All done" beside "needs a quick check" contradiction, is gone.
- **S9-01 changed test expectations.** `css-contrast.test.ts`: the `.home-track i` and `.home-dot` selectors are dropped from its non-text list because the per-child progress bar and the check-in dot they styled are gone (the test insists every listed selector exists). `app-shell.test.tsx`: the tabs are Home, Schedule, Records (was Home, Track work, Schedule), the active-tab and one-tap tests use Records. `router.test.tsx`: `/records` shows "Records" (was `/track` showing "Track work"); new cases that `/track` and `/track?week=...` land on `/schedule` with `view=week` and the query kept. `home.test.tsx`: the two Track work card tests (per-child "N left", "Last week needs a quick check") are replaced by one test that Home has exactly the Schedule and Records cards; the new-family test looks for Records; the tab-names and 44 px card-link tests say Schedule and Records; the briefing test waits for the Records link instead of the child's name (no per-child rows now). `s8b-fixes.test.tsx` N9 ("Nothing planned, not All done" on Home) now checks Home shows neither line, since the per-child progress rows no longer exist; the N10 test renders the Track page directly. `briefing.test.tsx`: the nudge link goes to `/schedule?view=week`, and the test that followed it to Track work and confirmed there is removed (that page has no route; S9-02 retires the card and page for good). `undo-bar.test.tsx` leaves the page by the Records tab. `track.test.tsx`: renders the page directly (`renderTrack`) instead of at `/track`; assertions unchanged.

- **S9-04 DateField is a text box plus a calendar button**, not a sheet: a nested sheet inside the Add assignment sheet and the fixed Year edit bar would fight over focus, so the calendar hangs under the field (above it for the edit bar), as wide as a phone allows, and swaps to the field's right edge when the left would pass the screen or sheet (the End field). Dates read "Nov 1, 2026"; "Nov 1" where tight; the week header "Oct 26 – Nov 1"; Home's date "Sunday, Nov 1". Weeks in the calendar start on Sunday (US).
- **S9-04 typing:** "11/1/2026", "Nov 1, 2026" and "2026-11-01" are read, but only with a four-digit year and a real day, so half a date never sets a different one. Text kept as typed while focused; tidied on leaving. Emptying the box clears the date; nonsense leaves the last good date. Optional dates (event start/end, copy's new start) offer Clear in the calendar.
- **S9-04 the Plan debug view keeps its native "Plan as of" date box**: it is behind the developer flag, not parent-facing.
- **S9-04 changed test expectations.** Date text is US style: `home.test` ("Wednesday, Oct 28", "Dec 8", "Dec 1", `longDate` "Saturday, Oct 31", `weekSpan` "Oct 26 – Nov 1"), `this-week`, `plan-debug` ("Nov 2 – Nov 8", "Oct 19 – Oct 25"), `track` ("Oct 19 – Oct 25", "Keep Dec 1", "Move to Dec 7"). - **S9-05 one line, the existing words.** Home shows the single most important line across children (late or stalled work, then plan problems, then a heavy week; ties go to the earlier child) in the briefing's own wording ("Math 3 will finish about 3 weeks late."), and a "Review" action to Schedule · Week, where that line has its Move end / Keep buttons. - **S9-02 what Update status writes.** The check-in API only takes a finished week and replaces that whole week, so Update status from a current-week bar or the Year edit bar works against the last finished week ("They got to p. 138", keep the end date or move it): the plan resumes from that position this week. Its save keeps the week's other stored answers and swaps in this bar's (`statusBody`), marks the week reviewed, and is the only thing that writes a check-in now. With All children and an assignment for several children it first asks "Whose progress?". If the assignment was not planned in that week it says there is nothing to update yet.

In the Year view it is in the edit bar's More menu, above "Update time estimate".

The API's `/api/check-ins/weeks` stays but the web no longer calls it. The `useLastWeekCheckIn` hook file keeps its name but only `useWeekCheckIn` remains.
- **S9-02 smoke scripts.** `scripts/smoke/scenarios/track.mjs` and the Track work lines in `tap-targets.mjs`, `axe.mjs` and `scripts/README.md` describe the old page; S9-09 updates them.
- **S9-02 changed test expectations.** `track.test.tsx` becomes `update-status.test.tsx`: the question card, Not quite, per-bar checks, Add progress and Save check-in tests are removed with those features; the Update status tests now start from a Week bar (bar, then "Update status for ..."), save with one PUT straight away (no Save check-in step), and the finished-week test asserts no checks or Save check-in. New tests: the card and nudge are gone, `/track` redirects, the Year edit bar flow, whose progress, `statusBody`. `briefing.test`: the three nudge tests become one (no nudge, no weeks request). `s8b-fixes`: N10 (the "Not quite" hint) is removed with its feature, and its now-unused import. `test/render.tsx` no longer has `renderTrack` (back to the original).
- **S9-03 seven switches, not six.** The ticket lists six fields but its "Days and hours" style needs a total; so there is a seventh switch, **Total hours** (one total instead of hours by subject). The rules the API enforces and the form keeps: at least one thing tracked; core and non-core hours need hours by subject; total hours and hours by subject are exclusive (the subjects add up to the total). A style is only the starting switches; a mix that matches no style is stored as `custom`.
- **S9-03 "Detailed log" is hours by subject, notes and books** (as the ticket words it), without school days. Every entry still has the visible "Count as a school day" switch (S9-07); the School days switch decides whether school days show in totals and exports.
- **S9-03 core is a plain flag, default non-core.** `subject.core boolean NOT NULL DEFAULT false`: a subject is core only once marked, so Log setup lists every active subject with Core | Non-core (Non-core preselected). It is set in Log setup (written only for subjects that changed, and only when core and non-core hours are on) and on the subject form's "Core subject" switch (sent only when changed, so existing subject requests are unchanged).
- **S9-03 no data lost.** The setup only hides or shows fields; nothing stored is removed. Turning core and non-core hours off and on again in the form keeps the marks (tested); entries keep every typed value whatever the setup (S9-07).
- **S9-03 wording and link.** The help line is "Not sure which fits? Your state's rules decide what to keep." with a link to HSLDA's page of state laws (https://hslda.org/legal, opens in a new tab); a test asserts no state name appears on the screen. No claim of compliance anywhere.
- **S9-03 Records after setup** shows only "Your log tracks ..." and Change log setup until S9-07/08 add logging and totals.
- **S9-03 changed test expectations.** API: `family.test`, `tester2.schedule.test` gain `logSetup: null` in the exact family shape; `subjects-list.test` gains `core: false` in the exact subject shape. Web: `helpers/fake-api.ts` BODY_KEYS (the registry of keys the API accepts) gains `logSetup` for PATCH /api/family and `core` for subject POST/PATCH; `settings-form.test` fixture gains `logSetup: null`. New: API `log-setup.test`, db `log-setup-migration.test` and `validate.sql`, web `log-setup.test`.
- **S9-07 new table, not the old `log_entry`.** `record_entry` (017) holds what the parent typed: one row per child per entry, first and last day, the school-day switch, how many days it counts (worked out at save), typed minutes (by subject as JSON, total, home, away), notes and books. The 001 `log_entry` (assignment check-offs, unused) and `progress_checkin` are untouched; old check-ins keep steering the plan and never appear as entries. Nothing here is read by the plan, and nothing in the plan fills an entry in (the API has no such path; a test compares the plan and the plan tables before and after create, edit, delete and undo).
- **S9-07 several children = several rows.** The form's All children / one or several chips send `childIds`; the API stores one entry per child, each with its own school-day count (a child-only day off shows in that child's count only). A family with one child is not asked who (nothing to choose; it is not a plan value). The first day, children and every hours box start empty.
- **S9-07 school days.** Switch off: 0. One chosen date: 1, even on a weekend (the parent chose that day). A run: each school-calendar day in it, family and child days off excluded; a weekend-only run counts 0. The entry's summary says how many days it counts.
- **S9-07 hours.** Typed as hours and minutes (minutes 0-59), stored as whole minutes. A day holds 24 hours: each typed amount (subjects added together, total, home plus away) must fit in 24 h times the calendar days of the entry, checked in the form and in the API. A run longer than 366 days is refused.
- **S9-07 edit and delete.** Edit shows the entry's own values; it sends only the fields the setup tracks, so hidden fields keep their typed values (nothing is lost when a field is turned off). An entry stays its child's. Edit and delete leave the family's one undo entry (`logEntry` step; create does not), and `api/client.ts` asks the undo bar after them. Delete has no confirm: the bar's Undo is the way back.
- **S9-07 Records list shows every entry** for now; S9-08 narrows it to a range.
- **S9-07 changed test expectations.** `log-setup.test.tsx` stubs the two extra requests Records now makes (children, log entries); web `fake-api` BODY_KEYS gains the two log-entry bodies. No other expectation changed. New: API `record-entries.test`, db `record-entries-migration.test` + `validate.sql`, web `log-entries.test`.
- **S9-08 how an entry meets a range.** By its first day (an entry is counted whole in the range its first day falls in; its hours cannot be split across a boundary). The Records list filters the same way. No range is sent as "everything" for the API; the page always picks one (default Year).
- **S9-08 hours and the splits.** An entry's hours are its subject minutes added up when it has any, else its typed total. Core and non-core use each subject's current flag; time typed only as a total counts in the total but in neither split. Books are listed once (case and spacing ignored).
- **S9-08 All children.** Hours add up across children; school days show the most any one child logged (adding would count a shared day twice); one child shows exactly that child's. Ranges: This week, Year (the live assignments' first to last day, else the calendar year), Fall and Spring (the family's names and dates from S9-06, else the halves either side of New Year when the year spans it; hidden ones are left out), the family's own terms, and Custom dates (two DateFields).
- **S9-08 page.** Wording (exact, from the ticket) under the page; empty log: "Nothing logged yet." and the Log button; a range with no entries: "Nothing logged in these dates." Big numbers only for tracked fields; hours by subject uses the subject colours. Records only reads assignments (for the Year dates).
- **S9-08 changed test expectations.** `log-entries.test`: the "logging never calls the plan" test now allows read-only GET /api/assignments (Records reads it for the Year dates) and still forbids any plan, check-in or assignment write. `log-setup.test` and `log-entries.test` stub the assignments and totals requests Records now makes. `router.test`: the old-link redirect check waits for the redirect (it flaked once under a loaded gate; no expectation changed). New: API `record-totals.test`, web `records-totals.test`.
- **S9-11 made on the device.** The CSV and the printable summary are built in the browser from the entries Records already holds (no new API route, nothing sent anywhere; the download is a local file). The totals arithmetic therefore exists twice, in the API (`recordTotals.ts`, for Records) and in `exportData.ts` (for exports); both are tested on the same rules (hours of an entry, core split, books once, a family's school days = the most any one child logged).
- **S9-11 the file.** First line: the wording (S9-08, exact). Then a header and one row per entry (oldest first), or per child in Totals. Date (first day) and Child are always there; "Last day" only when some entry is a run. Ticks offered: only fields the family tracks (notes only entry by entry); a ticked column with nothing in the range is left out (a 0 or blank everywhere counts as nothing), and all data stays stored. Hours are decimal hours (3.5) in the CSV; dates are ISO (2026-11-02) so a spreadsheet reads them. Subjects are one column each ("Math (hours)"); books are joined with "; ".
- **S9-11 CSV safety.** Every text cell, header cells included, that starts with `=`, `+`, `-`, `@`, a tab or a return gets a leading `'` before quoting (ROADMAP rule), so "=HYPERLINK(...)" in a note, a subject name or a book exports safely; numbers are never touched. Tested.
- **S9-11 the sheet.** From/To (DateFields, starting at the Records range), children (starting at the Records choice), Each entry | Totals, a tick per column, Download CSV, Print summary. No children or backwards dates disables both. The file is named `records-{from}-to-{to}.csv`.
- **S9-11 printable summary.** Print summary puts a hidden section in the page (one `.print-page` per child: name, dates, totals for the ticked fields, the entries when "Each entry", the wording), marks the page as printing, and calls the browser's print; a print stylesheet hides the app, shows only that section and breaks the page after each child, so "Save as PDF" gives one tidy page per child. Checked by printing the demo to a PDF: two pages for two children. Slip rule not needed.
- **S9-11 changed test expectations.** None changed. New `records-export.test.tsx`.
