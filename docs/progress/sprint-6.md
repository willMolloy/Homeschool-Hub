## Decisions (conservative calls on ambiguous points)

- **S6-01 ties.** Rows with the same `updated_at` (one transaction) fall back to `id`, which is arbitrary but stable.
- **S6-02 replacing an edit.** `updated_at` is set with `clock_timestamp()` rather than `now()`, so two edits in one transaction still order. Saving the same assignment, child and week again replaces its amount and mode and moves it to the end of the edit order.
- **S6-02 who gets a 400 or a 404.** Everything wrong with the body or its references (misaligned or finished week, amount out of range, unknown or foreign or archived assignment, a child that is archived or not on the assignment) is a 400 `invalid_request`. A missing or foreign adjustment id on DELETE is a 404. A foreign id looks exactly like an unknown one, so nothing leaks.
- **S6-02 the current week.** `weekStart` may be the family's current week (it is "not before" it); adjusting the current week is the whole point of S6-03. Whole weeks only, two decimals, 0 up to the assignment's total.
- **S6-02 reading past weeks.** `GET` accepts any aligned week (past ones too, so the app can show what was set); only `PUT` refuses a finished week.
- **S6-02 demo family.** Not blocked: like check-ins, an adjustment only reshapes the plan and the demo is for looking around at exactly that.
- **S6-03 which sheet.** The shown week decides: the current or a coming week gets the new amounts sheet (`ahead`), a past week keeps the check-in sheet untouched. So on the default view the "Make an adjustment" button no longer reopens last week; last week is still checked in on its card and by switching to it.
- **S6-03 changed test expectations.** `this-week.test.tsx` opened the check-in sheet on `/` (the current week). That now opens the new sheet, so its `openSheet` helper and the "save refreshes last week's prompt" test open on `/?week=2026-10-19` (last week). Every assertion in them is unchanged. `BODY_KEYS` in the fake API gained `PUT /api/week-overrides`.
- **S6-03 starting amounts.** Taken from the plan for the shown week (the child's days in it, rounded to 2 places), so an adjustment already saved is already in the starting value. A row shows when the child has work that week or an adjustment of their own for it.
- **S6-03 "back to the plan".** The plan response has no "without adjustments" amount, so a row cannot know the plan's own amount once adjusted. A row with the child's own saved adjustment gets a "Back to plan" button instead, which sends the DELETE on Save (and can be undone before saving). A row with no adjustment that is stepped back to where it started sends nothing. An adjustment set for every child (`childId` null) is shown in the amount but cannot be removed from one child's sheet.
- **S6-03 the end-date question.** One choice for the whole sheet, shown only once an amount moved (not for removals), defaulting to "Keep the end date", other option "Move the end date" (later if less, sooner if more). The check-in no longer asks per row (T-09), so there is no AbsorbChoice to reuse; this is a two-button group in the check-in's own style.
- **S6-03 limits.** Steps are 5 for minutes and 1 otherwise (the check-in's); the most an amount can be is what is left of the assignment, never below the current amount. Save sends one PUT per changed row in order, then closes the sheet and refreshes the plan; a refused save shows the message and keeps the sheet. The engine, not the sheet, handles the case where the plan cannot keep the end date.
- **S6-03 not checked.** The 360 px layout and 44 px targets come from CSS (44 px buttons, rows wrap) but jsdom has no layout, so they were not measured.
- **S6-04 removed tests.** `test/missed-day.test.tsx` (the S4-10 and S4b-07 sheet tests: offered days, today preselected, save for one child or everyone, errors, Cancel) is deleted with the feature it tested; nothing else covered them. Two tests were added: This Week has no "Missed a day?" control while the check-in card is still there, and an existing `missed` day off is still listed as "Missed day" under Days off and can't be picked as a kind on a new one.
- **S6-04 left alone.** The `missed` blocked kind (API, engine `pastMissedDays`, `KIND_LABELS`) and the Days off form's rule that an existing missed day keeps its kind when edited. Only the comment there changed, since the button it named is gone.
- **S6-05 migration number.** `013_undo.sql`. `db/test/validate.sql`, `db/README.md` and a migration test (`db/test/undo-migration.test.ts`) are in step.
- **S6-05 `original` stays nullable.** The ticket says NULL; every existing row is filled by the migration and every API create stores it, but a row inserted by hand (a test or script) has none. Reset (S6-07) answers 409 for such a row. The column only has a "must be an object" CHECK.
- **S6-05 what `original` holds.** `title, subjectId, unitType, totalUnits, weightPerUnit, weekdays, startDate, endDate, childIds`, as sent on create (`weekdays` null = follow the subject). For existing rows it is their values at migration time, since the true creation values are gone.
- **S6-05 `undo_entry`.** `label` (1 to 300 characters) and `inverse` (a JSON object the API reads in S6-06), `created_at`; deleted with the family.
- **S6-06 what is recorded.** Every `PATCH /api/assignments/:id` (drag, edit, weight, archive or restore), day off create (single and bulk, one entry), edit and delete, and week adjustment `PUT` and `DELETE`. The ticket names a day off "created or deleted"; an edit to a day off is recorded too, because leaving it out would leave an older entry that undo could apply on top of a newer change. Creating an assignment is not recorded (the ticket's list has no create, and undoing it would mean deleting a row that progress can point at) and, like the other writes, does not touch the entry.
- **S6-06 the entry format.** `inverse` is `{ steps: [...] }`; a step is `assignment` (the fields to put back, with its children and its weekday history), `blockedRange` or `weekOverride` (`set` is the state to restore, `null` = the row should not exist), or `weightChoices` (ids to delete). A week adjustment that replaced an earlier one restores the old amount, mode and its old `updated_at`, so the C1 edit order is exact.
- **S6-06 weight choices.** An edit that records a weight choice (S2b-07) also stores those rows' ids in the inverse; undo deletes them, so an undone nudge does not steer the next suggestion (`recordWeightChoices` now returns the ids; callers that ignored its result are unchanged).
- **S6-06 no-op edits.** An assignment or day-off PATCH that leaves every stored field as it was does not replace the entry.
- **S6-06 labels.** "Moved {title}" (only dates sent), "Changed the weight of {title}" (only weight), "Archived / Restored {title}", otherwise "Changed {title}"; "Added a day off", "Added N days off", "Changed a day off", "Removed a day off"; "Adjusted {title}", "Removed an adjustment to {title}". Longer than 300 characters is cut.
- **S6-06 responses.** `GET /api/undo` is `{ label, createdAt }` or JSON `null`. `POST /api/undo` is `{ label }`; 404 `not_found` with nothing to undo; 409 `cannot_undo` ("That change can't be undone any more.") and the entry is dropped when a row it restores is gone, a reference no longer exists (any integrity error) or a check-in now pins the dates it would restore. The undo runs in one transaction, so a refused one changes nothing.
- **S6-07 response.** `{ assignment, kept }`: the assignment as `GET /api/assignments` shows it, and `kept` lists the fields that kept their current value, `"subject"` and/or `"children"` (empty when nothing was kept).
- **S6-07 archived originals.** The original subject is kept as current when it is archived (or gone) and differs from the current one; a subject already current is never reported. For children the rule is the same applied to the whole list: if any original child is archived, the current children stay and `"children"` is reported (dropping just the archived ones would give a set the parent never had).
- **S6-07 what else goes back.** The weekday change history (`weekdays_from`, `previous_weekdays`) is cleared along with the days, so the plan is the created plan again, including for weeks before today; check-ins keep recording what happened. An archived assignment stays archived (reset restores values, not the archive state). A changed weight or unit records a weight choice like an edit does (a reset to no weight records "cleared"), and the undo takes those rows back.
- **S6-07 refusals.** 404 for an unknown, malformed or other family's id. 409 `no_original` for a row with no `original`. A 409 `check_in_outside` when the original dates would put the latest check-in's week outside the assignment (the same rule as moving dates); nothing is changed.
- **S6-07 undo.** One entry labelled "Reset {title}", with the assignment's earlier fields, the weight choices and every removed adjustment (same id and edit order). A reset that changes nothing (untouched assignment, no adjustments) records no entry.
- **S6-08 how the bar learns of a change.** `api/client.ts` announces every successful request that the API records as undoable (an assignment `PATCH` or reset, a day off create, bulk create, edit or delete, a week adjustment `PUT` or `DELETE`; a creation of an assignment is not one) through `onPlanChange`. `UndoProvider` answers with `GET /api/undo` and shows the label. One list, so a form, the timeline, the week sheet and the days-off page all get the bar without each calling it.
- **S6-08 where and how long.** `SignedInShell` mounts the provider and the bar, so it covers every signed-in page. It shows `{label}.` and an Undo button, in a fixed pill above the tab bar on phones (the timeline lifts it above its open edit bar through `--edit-bar-height`). It is a `role="status"` and sits early in the document, so it is read out and a keyboard reaches it without tabbing through the page. It stays until the next change replaces it or the route's path changes (a `?week=` or `?child=` change does not count).
- **S6-08 after Undo.** The page remounts (`AppShell` takes a `contentKey`), so every list and picture reloads from the API; the bar goes. A 404 or 409 shows "That change can't be undone any more." in the bar (no button) and remounts the page too. Any other failure shows "Couldn't undo. Try again." and keeps the Undo button.
- **S6-08 reset on the edit bar.** The timeline edit bar has no "More", so **Reset to original** sits after Copy in the same row. It always shows (the browser does not know the original; the existing "Reset" beside the dates, which only undoes this visit's date moves, is unchanged). It opens the confirm dialog "Put {title} back to how you created it?"; Reset posts, swaps in the returned assignment, reloads the plan, and the bar offers "Reset {title}. Undo". A refusal (for example no saved original) shows in the dialog. The `kept` list is not shown in the app.
- **S6-08 changed test expectations.** `timeline-edit-bar.test.tsx` "the edit bar's order on phones" lists the edit bar's buttons exactly; it now ends with "Reset to original" (the new button). The fake API answers `GET /api/undo` with null by default.
- **S6-09 engine and version.** Two pure additive exports in `weights.ts`; no plan number changes, so `ENGINE_VERSION` stays 0.9.0 (S4-08 and S5-03's precedent). Invalid inputs (non-positive or non-finite) throw `EngineInputError`; `minutesPerDayFromWeight` is not rounded so a stored weight round-trips.
- **S6-09 units a day.** Total ÷ the number of days between start and end (both included) whose weekday is one of the form's Days chips (the assignment's own, else the subject's, else the family's school days). Days off and events are not subtracted; the pace line says "About", and the plan stays the engine's. No pace (no total, dates or matching day) shows a short prompt and no presets.
- **S6-09 what shows chosen.** Untouched, the option closest to the weight the form stands on (the suggestion when adding or after a unit change; the stored weight, else subject default, else built-in, when editing or copying): a preset if within 7.5 minutes of it, otherwise Custom prefilled with the minutes. The hint says the suggestion's source and "That's about N min a day" (editing: "now"). Tapping the already-chosen preset counts as an answer (it saves a weight, not the suggestion). After a pick that differs from the suggestion, "Use about N min" goes back to it.
- **S6-09 saving.** Untouched adding saves as before (a learned suggestion explicitly, subject or built-in as null). Untouched editing never sends a weight, even when the dates or total change: the weight per unit stands and the minutes a day shown follow the new pace. A pick saves `weightFromMinutesPerDay(minutes, pace)`. Custom minutes must be more than 0, at most 1,440, two decimals.
- **S6-09 lost ability.** The raw weight field was the only way to clear an assignment's own weight back to "follow the subject default" from the form; that is gone with it (the API still accepts null, and a subject's default stays on the subject form).
- **S6-09 changed test expectations.** The weight-field tests in `assignments-screen.test.tsx` now drive the effort question: same cases (add, untouched suggestion to null, minutes unit, bad input, edit PATCHes only changes, unit change, learned/subject/built-in hints, S2c-04 waiting) with presets, Custom and the "That's about N min" hint in place of typing a weight; hint assertions became prefix matches. "Clearing the weight on edit sends null" is replaced by "an edit that leaves the effort alone never sends a weight". `assignment-copy.test.tsx` checks the preselected "15 minutes" instead of the weight field; `timeline-add.test.tsx` expects the effort legend after Total and no "More" or weight field. New: `assignment-effort.test.tsx`, `engine/test/weights.minutes.test.ts`.
- **S6-10 the base weight.** The weight in effect for the selected assignment: its own, else its subject's default for the same unit, else the built-in (`weightPerUnitOf`). A nudge sends the new number as the assignment's own weight, so a following assignment becomes explicit from then on. Heavier is x 1.25, Lighter x 0.8, rounded to two decimals and kept within 0.01 to 100; a step that would round back to the same number moves 0.01 instead (so 0.01 can still go heavier). A direction is disabled at its limit, so no request is sent that changes nothing. Tapping Heavier twice compounds from the saved weight (x 1.5625, rounded).
- **S6-10 carrying forward and undo.** Nothing new on the API: the weight-only PATCH already records a weight choice per child for pages and chapters (S2b-07) and an undo entry labelled "Changed the weight of {title}" (S6-06), which takes the choice back. For lessons and minutes there is no learning (D17), so the nudge only changes that assignment. API test: the child's next suggestion (and a later assignment) follows the nudge, not another child's, and an undo restores the earlier suggestion.
- **S6-10 placement (note for S6b-05).** Built as ticketed: Heavier and Lighter sit in the edit bar's last row after Copy, with Reset to original. S6b-05 will move them (with Reset) behind a small "More"; doing it now would have meant reworking S6-08's button and tests for a layout that ticket replaces.
- **S6-10 changed test expectations.** `timeline-edit-bar.test.tsx` "the edit bar's order on phones" lists the buttons exactly; it now has Heavier and Lighter between Copy and Reset to original.
