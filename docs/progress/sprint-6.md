## Decisions (conservative calls on ambiguous points)

- **S6-01 ties.** Rows with the same `updated_at` (one transaction) fall back to `id`, which is arbitrary but stable.
- **S6-02 replacing an edit.** `updated_at` is set with `clock_timestamp()` rather than `now()`, so two edits in one transaction still order. Saving the same assignment, child and week again replaces its amount and mode and moves it to the end of the edit order.
- **S6-02 who gets a 400 or a 404.** Everything wrong with the body or its references (misaligned or finished week, amount out of range, unknown or foreign or archived assignment, a child that is archived or not on the assignment) is a 400 `invalid_request`. A missing or foreign adjustment id on DELETE is a 404. A foreign id looks exactly like an unknown one, so nothing leaks.
- **S6-02 the current week.** `weekStart` may be the family's current week (it is "not before" it); adjusting the current week is the whole point of S6-03. Whole weeks only, two decimals, 0 up to the assignment's total.
- **S6-02 reading past weeks.** `GET` accepts any aligned week (past ones too, so the app can show what was set); only `PUT` refuses a finished week.
- **S6-02 demo family.** Not blocked: like check-ins, an adjustment only reshapes the plan and the demo is for looking around at exactly that.
- **S6-03 which sheet.** The shown week decides: the current or a coming week gets the new amounts sheet (`ahead`), a past week keeps the check-in sheet untouched. So on the default view the "Make an adjustment" button no longer reopens last week; last week is still checked in on its card and by switching to it.
- **S6-03 changed test expectations.** `this-week.test.tsx` opened the check-in sheet on `/` (the current week). That now opens the new sheet, so its `openSheet` helper and the "save refreshes last week's prompt" test open on `/?week=2026-10-19` (last week). Every assertion in them is unchanged. `BODY_KEYS` in the fake API gained `PUT /api/week-overrides`.
- **S6-03 starting amounts.** Taken from the plan for the shown week (the child's days in it, rounded to 2 places), so an adjustment already saved is already in the starting value. A row shows when the child has work that week or an adjustment of their own for it.
- **S6-03 "back to the plan".** The plan response has no "without adjustments" amount, so a row cannot know the plan's own amount once adjusted. A row with the child's own saved adjustment gets a "Back to plan" button instead, which sends the DELETE on Save (and can be undone before saving). A row with no adjustment that is stepped back to where it started sends nothing. An adjustment set for every child (`childId` null) is shown in the amount but cannot be removed from one child's sheet.
- **S6-03 the end-date question.** One choice for the whole sheet, shown only once an amount moved (not for removals), defaulting to "Keep the end date", other option "Move the end date" (later if less, sooner if more). The check-in no longer asks per row (T-09), so there is no AbsorbChoice to reuse; this is a two-button group in the check-in's own style.
- **S6-03 limits.** Steps are 5 for minutes and 1 otherwise (the check-in's); the most an amount can be is what is left of the assignment, never below the current amount. Save sends one PUT per changed row in order, then closes the sheet and refreshes the plan; a refused save shows the message and keeps the sheet. The engine, not the sheet, handles the case where the plan cannot keep the end date.
- **S6-03 not checked.** The 360 px layout and 44 px targets come from CSS (44 px buttons, rows wrap) but jsdom has no layout, so they were not measured.
- **S6-04 removed tests.** `test/missed-day.test.tsx` (the S4-10 and S4b-07 sheet tests: offered days, today preselected, save for one child or everyone, errors, Cancel) is deleted with the feature it tested; nothing else covered them. Two tests were added: This Week has no "Missed a day?" control while the check-in card is still there, and an existing `missed` day off is still listed as "Missed day" under Days off and can't be picked as a kind on a new one.
- **S6-04 left alone.** The `missed` blocked kind (API, engine `pastMissedDays`, `KIND_LABELS`) and the Days off form's rule that an existing missed day keeps its kind when edited. Only the comment there changed, since the button it named is gone.
- **S6-05 migration number.** `013_undo.sql`. `db/test/validate.sql`, `db/README.md` and a migration test (`db/test/undo-migration.test.ts`) are in step.
- **S6-05 `original` stays nullable.** The ticket says NULL; every existing row is filled by the migration and every API create stores it, but a row inserted by hand (a test or script) has none. Reset (S6-07) answers 409 for such a row. The column only has a "must be an object" CHECK.
- **S6-05 what `original` holds.** `title, subjectId, unitType, totalUnits, weightPerUnit, weekdays, startDate, endDate, childIds`, as sent on create (`weekdays` null = follow the subject). For existing rows it is their values at migration time, since the true creation values are gone.
- **S6-05 `undo_entry`.** `label` (1 to 300 characters) and `inverse` (a JSON object the API reads in S6-06), `created_at`; deleted with the family.
- **S6-06 what is recorded.** Every `PATCH /api/assignments/:id` (drag, edit, weight, archive or restore), day off create (single and bulk, one entry), edit and delete, and week adjustment `PUT` and `DELETE`. The ticket names a day off "created or deleted"; an edit to a day off is recorded too, because leaving it out would leave an older entry that undo could apply on top of a newer change. Creating an assignment is not recorded (the ticket's list has no create, and undoing it would mean deleting a row that progress can point at) and, like the other writes, does not touch the entry.
- **S6-06 the entry format.** `inverse` is `{ steps: [...] }`; a step is `assignment` (the fields to put back, with its children and its weekday history), `blockedRange` or `weekOverride` (`set` is the state to restore, `null` = the row should not exist), or `weightChoices` (ids to delete). A week adjustment that replaced an earlier one restores the old amount, mode and its old `updated_at`, so the C1 edit order is exact.
- **S6-06 weight choices.** An edit that records a weight choice (S2b-07) also stores those rows' ids in the inverse; undo deletes them, so an undone nudge does not steer the next suggestion (`recordWeightChoices` now returns the ids; callers that ignored its result are unchanged).
- **S6-06 no-op edits.** An assignment or day-off PATCH that leaves every stored field as it was does not replace the entry.
- **S6-06 labels.** "Moved {title}" (only dates sent), "Changed the weight of {title}" (only weight), "Archived / Restored {title}", otherwise "Changed {title}"; "Added a day off", "Added N days off", "Changed a day off", "Removed a day off"; "Adjusted {title}", "Removed an adjustment to {title}". Longer than 300 characters is cut.
- **S6-06 responses.** `GET /api/undo` is `{ label, createdAt }` or JSON `null`. `POST /api/undo` is `{ label }`; 404 `not_found` with nothing to undo; 409 `cannot_undo` ("That change can't be undone any more.") and the entry is dropped when a row it restores is gone, a reference no longer exists (any integrity error) or a check-in now pins the dates it would restore. The undo runs in one transaction, so a refused one changes nothing.
