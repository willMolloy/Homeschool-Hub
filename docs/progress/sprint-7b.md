## Decisions (conservative calls on ambiguous points)

- **S7b-01 the endpoint.** `PUT /api/week-overrides/batch` takes `{ weekStart, set: [{ assignmentId, childId, plannedUnits, mode }], remove: [overrideId] }` (each list up to 100; at least one row in all). The checks are the single endpoint's (week aligned and not finished; assignment, child and total), run per row in one transaction, so a bad row saves nothing and records no undo. It records one undo entry whose steps put each row back (set, replaced or removed). Duplicate `set` rows (same assignment and child) or duplicate `remove` ids are refused (400); a `remove` id that is not this family's row for that week is a 404. It returns `{ overrides }` (the rows set).
- **S7b-01 the label.** Several rows: "Adjusted 3 assignments for Frank, week of Nov 2" (the undo bar adds the full stop); rows for more than one child (or a mix of one child and every child) read "for several children"; all for every child read "for every child". One row reads exactly as the single endpoint does ("Adjusted Treasure Island for Frank, week of Nov 2", or "Removed the adjustment to ..." for a lone removal). A save mixing removals and sets counts them all as "assignments adjusted".
- **S7b-01 the web client.** The sheet always sends the batch (even for one row), so one tap of Save is one request. `api/client.ts` lists the batch path among the plan-changing requests so the undo bar refreshes. The single-row PUT and DELETE endpoints are unchanged and still refresh it.
- **S7b-01 changed test expectations.** `week-adjustment.test.tsx`: the sheet's tests used to expect one `PUT /api/week-overrides` per changed row and a `DELETE` for a row taken back; they now expect one `PUT /api/week-overrides/batch` (body in `set` / `remove`), same values. The fake API's allowed body keys gain the batch. `undo-bar.test.tsx`: the batch path is added to the list of undoable requests. Nothing weakened.
- **S7b-02 pace and the estimate.** "At the assignment's pace" is units a day from its total, dates and days (its own days, else the subject's, else every school day), the same pace the assignment form uses. "We estimated about N min a day" is the stored (or subject, or built-in) weight at that pace, in whole minutes. The preselected choice is the nearest of 15/30/45/60 (as the form's `optionFor` does: within 7.5 minutes), else Custom prefilled with the whole minutes. Custom takes more than 0 and at most 1,440 minutes (the form's limit). With no usable pace (no days in the dates) the sheet says to add dates and days first.
- **S7b-02 the carry-forward line.** Shown for pages and chapters only (the units whose usual weight is learned from earlier work, `isLearnedUnit`); lessons and minutes get no such line, since the next book would not start from it. One child: "Frank's next Literature books will start from this too."; several children on the assignment: "Their next ...".
- **S7b-02 the undo label.** The API's label for a weight-only edit changed from "Changed the weight of {title}" to "Updated the time estimate for {title}" (the ticket's wording; "weight" is gone from every parent-facing text). Any other PATCH containing only `weightPerUnit` (the form never sends that alone) reads the same.
- **S7b-02 removed.** `nudgedWeight` (`timeline/nudge.ts`) and `useAssignmentEdit.setWeight` had no other user, so both are deleted with their unit tests.

- **S7b-04 how the engine learns about adjustments.** `forecastOutcome(plan, checkIns, calendar)` keeps its signature and the web briefing only has plans, so the plan now carries what the forecast needs: `adjustedWeeks` (the first day of every week with a week adjustment for this assignment and child, or every child), and `weekdaysFrom` / `previousWeekdays` (set only when the days really changed mid-assignment, S4-01b). **ENGINE_VERSION 0.9.0 to 0.10.0** (new plan outputs, a MINOR bump; no existing number changed).
- **S7b-04 the rule (also in the engine doc comment).** (1) Check-in weeks with an adjustment are left out of the observed pace; fewer than 2 left gives no forecast. (2) Pace is each included week's gain over that week's capacity (the same figure as before when nothing is left out: the weeks telescope). (3) With a weekday change: if at least 2 check-in weeks lie on or after the change, only those are measured and the forecast uses the new days; otherwise, if at least 2 lie before it, those are measured and the pace is carried over as a weekly pace (multiplied by old days a week over new days a week, counting only school days), so a change with no new check-in leaves the finish where it was (it can differ by a few days because the days it lands on differ); with fewer than 2 weeks either side, all weeks are used as before. The projection still starts after the latest check-in week, adjusted or not.
- **S7b-04 the no-progress line.** "No progress on X in the last N weeks" uses the same rule (it moved from the web into the engine as `noRecentProgress`, re-exported by `briefingLines.ts`), so a week the parent deliberately set to 0 doesn't claim the child made no progress.
- **S7b-04 changed test expectations.** `engine-version.test.tsx` expects 0.10.0; two web plan fixtures (`plan-debug`, `this-week`) gain the three new fields (the type requires them). The briefing refetches its plans after the PATCH, so the line goes. An assignment shared by two children moves for both (the end belongs to the assignment).

- **S7b-10 the count.** `capacityDays` (engine, `pace.ts`) sums the capacity the plan spreads over: school days on the assignment's own days (its list, else its subject's, else every school day), minus days off for that child, with an event that skips the subject counting 0 and a lighter one partly. A test checks `total / capacityDays` equals the plan's own `baseRate` in the review's case (Nov 2 to Jan 29 with Thanksgiving, the Christmas break and a Tuesday skip). No plan output changed, so ENGINE_VERSION stays 0.11.0.
- **S7b-10 the endpoint.** `POST /api/plan/pace` takes up to 500 drafts (`subjectId` or null, `childIds`, dates, `weekdays` or null) and answers, per draft, the days for each child and the smallest ("the busiest child sets the pace"). It is a POST only because of the list of drafts; it reads and saves nothing and is open to the demo family (it isn't a write). Validation matches the other schedule routes (400 for no drafts, no child, dates out of order or over 1,096 days, bad days, unknown keys).
- **S7b-10 the web.** `usePace` / `requestPace` batch every request made in the same tick into one POST (a list of cards is one request). The form asks after 250 ms of typing, always with the days it shows (`dayChoice.shown`); until the answer comes, or if the request fails, it counts weekdays between the dates as before. On Add/Save with an effort pick the form asks afresh and uses that answer, so a weight never rests on a count still loading. With several children the smallest count is used and a line says whose it is ("Frank has the fewest school days here, so this counts Frank's.") when they differ. Zero days gives no pace (the form asks for dates and days, as for an unfilled form).
- **S7b-10 cards, hints and the estimate sheet.** Assignment cards and the "Update time estimate" sheet (S7b-02) use the same count at the assignment's own days; the hints get it through the form's pace. "The plan's own rate" is read as total over those days (what the plan's `baseRate` is before any check-in); I did not read the live plan's rate per card, because that needs a plan for the whole span of every listed assignment.

- **S7b-11 the window.** "This year" is the first day up to the day before next year's first day (an assignment starting on or after next year's first day isn't a source, so an earlier run's copies never are). The old rule was "on or after the first day". The empty message is now "No assignments start in that year."
- **S7b-11 already copied.** A source is left out when a non-archived assignment with the same subject, title, the same children (as a set) and exactly the shifted dates exists. The panel says "{N} to copy · {M} already copied", or "{M} already copied." with nothing left. Weight and days are not compared (the title, subject, children and dates identify the copy).
- **S7b-11 the undo.** `POST /api/assignments/bulk` takes an optional `undo: { label, append? }`. With it the request records one undo entry whose step deletes exactly the created ids (a new `assignmentsCreated` step, hard delete: their weight choices, adjustments and the rest cascade). Undo is refused with the usual 409 (and the entry dropped, nothing removed) once any created assignment has a check-in. Without `undo` a bulk create is still not undoable, so Add several and CSV import behave as before (the ticket's "the bulk create records an undo entry" is read as the copies' bulk create; say if Will wants those undoable too). A copy in chunks of 50 is several requests: the later chunks send `append: true`, adding their ids to the first chunk's entry and setting the label to the count so far, so one Undo removes all of them (and a retry after a failed chunk appends to what was created). The label is "Copied {N} assignments to 2027–28" (year copy) or "Copied {N} assignment(s) to {Child}". The web client now treats a bulk POST as a plan change, so the undo bar refreshes after Add several and CSV import too (it finds nothing new there).
- **S7b-12 what is left out.** With a target chosen, an assignment is left out when the target child is already on it, or has a non-archived assignment with the same subject and title on the same dates as the original or as the shifted copy (when a new start date is typed). The line under "Copy to" says "1 already has Maggie." or "N already have Maggie." The Copy to field stays when the list empties, so the parent can pick another child. Nothing is left out until a target is chosen.
