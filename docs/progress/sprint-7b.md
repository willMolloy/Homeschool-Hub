## Decisions (conservative calls on ambiguous points)

- **S7b-01 the endpoint.** `PUT /api/week-overrides/batch` takes `{ weekStart, set: [{ assignmentId, childId, plannedUnits, mode }], remove: [overrideId] }` (each list up to 100; at least one row in all). The checks are the single endpoint's (week aligned and not finished; assignment, child and total), run per row in one transaction, so a bad row saves nothing and records no undo. It records one undo entry whose steps put each row back (set, replaced or removed). Duplicate `set` rows (same assignment and child) or duplicate `remove` ids are refused (400); a `remove` id that is not this family's row for that week is a 404. It returns `{ overrides }` (the rows set).
- **S7b-01 the label.** Several rows: "Adjusted 3 assignments for Frank, week of Nov 2" (the undo bar adds the full stop); rows for more than one child (or a mix of one child and every child) read "for several children"; all for every child read "for every child". One row reads exactly as the single endpoint does ("Adjusted Treasure Island for Frank, week of Nov 2", or "Removed the adjustment to ..." for a lone removal). A save mixing removals and sets counts them all as "assignments adjusted".
- **S7b-01 the web client.** The sheet always sends the batch (even for one row), so one tap of Save is one request. `api/client.ts` lists the batch path among the plan-changing requests so the undo bar refreshes. The single-row PUT and DELETE endpoints are unchanged and still refresh it.
- **S7b-01 changed test expectations.** `week-adjustment.test.tsx`: the sheet's tests used to expect one `PUT /api/week-overrides` per changed row and a `DELETE` for a row taken back; they now expect one `PUT /api/week-overrides/batch` (body in `set` / `remove`), same values. The fake API's allowed body keys gain the batch. `undo-bar.test.tsx`: the batch path is added to the list of undoable requests. Nothing weakened.
- **S7b-02 pace and the estimate.** "At the assignment's pace" is units a day from its total, dates and days (its own days, else the subject's, else every school day), the same pace the assignment form uses. "We estimated about N min a day" is the stored (or subject, or built-in) weight at that pace, in whole minutes. The preselected choice is the nearest of 15/30/45/60 (as the form's `optionFor` does: within 7.5 minutes), else Custom prefilled with the whole minutes. Custom takes more than 0 and at most 1,440 minutes (the form's limit). With no usable pace (no days in the dates) the sheet says to add dates and days first.
- **S7b-02 the carry-forward line.** Shown for pages and chapters only (the units whose usual weight is learned from earlier work, `isLearnedUnit`); lessons and minutes get no such line, since the next book would not start from it. - **S7b-04 the rule (also in the engine doc comment).** (1) Check-in weeks with an adjustment are left out of the observed pace; fewer than 2 left gives no forecast. (2) Pace is each included week's gain over that week's capacity (the same figure as before when nothing is left out: the weeks telescope). (3) With a weekday change: if at least 2 check-in weeks lie on or after the change, only those are measured and the forecast uses the new days; otherwise, if at least 2 lie before it, those are measured and the pace is carried over as a weekly pace (multiplied by old days a week over new days a week, counting only school days), so a change with no new check-in leaves the finish where it was (it can differ by a few days because the days it lands on differ); with fewer than 2 weeks either side, all weeks are used as before. ## Round 2 (the S7b-08 tester's N1 to N9)

- **S7b-15 the layout.** The row's button is now `flex-wrap: wrap`; the title has `flex: 1 1 9rem` with a 9rem minimum (or the row's width if narrower), and a state longer than 14 characters ("4 chapters (1 more than planned)") carries `data-long` and takes the whole line under the title. Short states ("2 of 3 ch.", the tick) stay on the title's line as before. Only the CSS rules and the marker are tested in jsdom (no layout there); the 360 and 390 px check is the tester's.
- **S7b-16 the cause and the fix.** The sheet seeded its choice once from the pace it had on first render (the weekday count) and the real pace arrived later, so the text moved and the chip did not. The starting choice is now derived from the current estimate on every render until the parent touches something, so it follows the pace. It is the preset within 2.5 minutes of the estimate, else Custom to the nearest 5 (about 37 opens on Custom 35, about 30 on 30). Save is off until the choice differs from where it started (tapping the chip already chosen is not a change; typing the same Custom number is not either). Changed expectation: the "refused save" test picks 45 first, since Save is off untouched.
- **S7b-17 the rule.** When a break is saved, if its dates are exactly a US holiday it is stored as before (the key, no offsets). Otherwise, if a whole holiday lies inside it (Thanksgiving inside Nov 23 to 27, the winter break inside Dec 21 to Jan 1), it is stored with that holiday's key and `holidayBefore` / `holidayAfter` (the days it runs before the holiday's first day and after its last: 3 and 0 for both of the tester's cases). If several holidays lie inside, the longest wins. Breaks with none inside keep S7b-13's behaviour. Applying places the break from `holidayBefore` days before the holiday's real first day to `holidayAfter` days after its last, using the holiday nearest where the break was; with days before it and a saved weekday, the start is moved to that weekday (the Monday of Thanksgiving week) but never later than the holiday's own first day. Results for 2027: Thanksgiving break Nov 22 to 26 (Monday to Friday), Christmas break Dec 20 to Jan 1 (the break started on a Monday and still does). The API accepts both offsets (whole numbers 0 to 60, only with a `holiday`); older templates have none and behave as in S7b-13.
- **S7b-17 changed test expectations.** The S7b-13 test that a break "next to" Labor Day stays plain used Sep 5 to 7, which now contains Labor Day and so is kept by it; it uses Sep 5 to 6. New tests for the tester's two cases, exact versus around, older templates, and the API fields.
