## Decisions (conservative calls on ambiguous points)

- **S7-01 no default dates.** Both first days start empty (the app stores no school-year dates); nothing is listed until both are valid dates. A line says what to do, and that only the plan is copied.
- **S7-01 what is offered.** Non-archived assignments starting on or after this year's first day whose subject is active and that still have an active child. An archived child is dropped from the copy (as `copyOfAssignment` does); an assignment with only archived children, or an archived subject, is left out because the API would refuse it.
- **S7-01 grouping.** Grouped by the children an assignment is for ("Frank", "Maggie", or "Frank, Maggie" for a shared one) rather than splitting a shared assignment under each child, so it is ticked once. Rows are ordered by start date, then title.
- **S7-01 partly saved.** Chunks of 50 go one after another and stop at the first failure. Earlier chunks stay: they are added to the list through a new `onAdded` on the `panels` render prop (adds rows without closing the panel). The panel stays open, says "Part 2 of 2 didn't save: <title>: <message> 50 copies were created.", and offers only the assignments not yet copied, so Copy again never duplicates. The list of sources is fixed when the panel opens, so the copies just created are never offered.
- **S7-01 copied as stored.** `weightPerUnit` and `weekdays` are copied exactly (null stays null); title is unchanged (no " (copy)"), because the copies are for another year.
- **S7-02 the picks.** Copy from (active children), then an optional Subject (only the subjects that child has work in), the child's assignments ticked (all by default), Copy to (every active child except the source), and an optional New start date. Nothing is listed until a source is chosen; a child with nothing says so.
- **S7-02 the shift.** The new start date is where the earliest *ticked* assignment starts; the others keep their gaps from it (so unticking the first changes the base). With no date, dates are unchanged. The preview line under each title shows the new dates as the date is typed.
- **S7-02 shared assignments.** An assignment Frank shares with Maggie is listed under "Frank, Maggie" and copied for the target child alone. Copying to a child who already has the same work makes a second assignment (not checked for or blocked: the parent ticks what they want).
- **S7-02 same rules as S7-01.** Assignments with an archived subject or no active child are not offered; chunks of 50; a failed chunk keeps the earlier ones and a retry sends only the rest. Titles are unchanged (no " (copy)").
- **S7-03 migration number.** 014 (`db/014_zoom_views.sql`); `db/test/validate.sql`, `db/README.md` and `db/test/zoom-views-migration.test.ts` are in step. The database checks only the shape (an object with `hidden` and `custom` lists, never NULL; the default is `{"hidden":[],"custom":[]}`); the API checks the contents, as 012 does for templates.
- **S7-03 rules the API enforces.** `hidden` holds only fall, spring, month, each once (Year is not hideable); `custom` has at most 5 views, each `{ id (uuid), name (trimmed, 1 to 30), start, end }` with real dates (2000 to 2100), start on or before end, at most 400 days (exactly 400 is fine); ids are unique; shown total (1 for Year + built-ins not hidden + custom) at most 6. Unknown keys anywhere are refused. The order of `custom` is kept (S7-05 reorders it). The total message says how many would show ("You can show up to 6 views; this shows 8.").
- **S7-03 changed test expectations.** `GET /api/family` now also returns `zoomViews`, so four exact `toEqual` bodies (`family.test.ts` three, `tester2.schedule.test.ts` one) and the web fixture `SETTINGS` in `settings-form.test.tsx` gain `zoomViews: { hidden: [], custom: [] }`; the fake API's allowed keys for `PATCH /api/family` gain `zoomViews`. Nothing else changed.
- **S7-04 how a view is chosen.** A custom view's zoom value is `custom:<its id>`, so the existing `Zoom` type widens without touching Fall, Spring or This month; the layout takes the family's views as `customViews` beside `zoom`. A custom view draws like Year, Fall and Spring (every lane, no month filtering); only This month filters lanes and has the month arrows.
- **S7-04 the range.** First grid day on or after the view's start to the last grid day on or before its end. No overlap, or a view that no longer exists, shows the whole grid (as Fall and Spring do). Detail follows the span as before (daily at 8 weeks or fewer).
- **S7-04 fallback.** The zoom state stays on the page; a zoom that is no longer in the row (hidden or deleted) is drawn as Year (the page's existing `shownZoom` rule). Covered by a test in S7-05 where views can be deleted.
- **S7-04 the row.** Order: Year, the built-ins the family hasn't hidden and the grid offers (Fall and Spring still only when the grid spans New Year), then its own views in stored order. With no grid there is only Year; the row stays hidden when only Year is left (S7-05 adds the Edit button, which needs a row to sit in; see there). The row is `overflow-x: auto` with buttons that don't shrink, so it scrolls sideways inside itself on phones and the page never does.
- **S7-04 loading the views.** `GET /api/family` is requested with the other timeline data and counts toward "loading" but not "failed": if it fails the timeline draws with the built-in views. No existing timeline test needed a change (an unregistered family request is a 404 in the fake API, which takes that path).
- **S7-05 row order versus the ticket's "Done when".** S7-04 says the row is Year, the built-ins still shown, then the family's views, and its example reads "Year, Spring, This month, Term 1". S7-05's Done-when lists "Year, Term 1-3, This month". The two disagree; I followed S7-04 (the explicit rule and the example), so hiding Fall and Spring and adding Term 1 to 3 shows Year, This month, Term 1, Term 2, Term 3. The built-ins cannot be reordered (only the family's own views move). Easy to change in `visibleZooms` if Will wants views before This month.
- **S7-05 the Edit button.** Text "Edit" (accessible name "Edit zoom views", which contains the visible word), no icon or badge, muted text with no fill, 44 px, at the end of the zoom row but outside the `Zoom` toggle group (so the group still holds only views). It shows whenever the timeline has a calendar, including when only Year is left (the toggle group is hidden then, as before) so hidden views can be brought back. The child chips share the `.tl-zoom` class, so they also scroll sideways instead of overflowing, a harmless side effect of S7-04.
- **S7-05 the sheet.** `ResponsiveSheet` (bottom sheet on phones, side panel on wide screens) titled "Zoom views". Year says "Always shown" with no switch; Fall, Spring and This month are switches (all three listed even when the grid doesn't span New Year and so isn't offering Fall and Spring, so a family can set them in advance); each custom view has Name, First day, Last day, Up, Down and Delete. Up is off for the first, Down for the last. Reordering moves only the family's own views.
- **S7-05 Add a view.** It adds an empty row to the sheet (name and the two days to fill in) rather than opening a second form; nothing is saved until Save. A row left blank is explained on Save ("Give it a name.", "Pick the first and last day.", and the date-order and 400-day rules in plain words) and nothing is sent. With six views showing it is disabled and the line "You can show up to 6 views." appears; switching a hidden built-in on is disabled then too (it would be the seventh).
- **S7-05 Save and Cancel.** Save sends one `PATCH /api/family` with only `zoomViews` (names trimmed; `hidden` in Fall, Spring, This month order; custom in the order shown) and then closes and updates the row. If nothing changed it closes without a request. Any other close (Cancel, the x, Esc, a tap outside) discards, and reopening starts from what is stored. A failed Save keeps the sheet and the changes and shows the API's message.
- **S7-05 new view ids** come from `crypto.randomUUID`, falling back to random bytes in uuid v4 form (`randomUUID` is only available on secure pages).
- **S7-05 deleted or hidden zoom.** Covered by tests: deleting the view being looked at, or hiding the built-in being looked at, shows Year.
- **S7-05 changed test expectation.** `timeline-view.test.tsx` "shows only what's essential" lists the visible buttons; "Edit" now follows "This month" (the ticket adds it). Nothing else changed.
- **S7-05 not checked.** The sheet and the row were tested in jsdom only; not looked at in a browser at 360 px (the layout reuses the existing form and sheet styles, rows wrap, and the zoom row scrolls inside itself).

## Pass B decisions

- **S7-06 what counts as finished.** A row is left out when neither the before nor the after plan has any units on or after today (`days` with `date >= today` and `units > EPS`). That covers an assignment that ended earlier and one whose check-ins finished it. Both plans are checked so a row is never dropped when the draft would give it work.
- **S7-07 the messages.** With the dates valid and nothing to add: "Nothing new to add: these breaks are already in your days off." when some were skipped as already days off, otherwise "No breaks in this range.". They replace the "0 breaks to add" heading and the "already in your days off" hint; Add breaks is disabled (no request). While the dates are invalid the button stays enabled so its error still shows.
- **S7-08 what is counted.** Every family-wide day off that starts before the chosen first day (any age; days off for individual children are not counted, they are already in the per-child note only when inside the year). Text: "1 day off before Aug 17, 2026 isn't included." / "N days off before ... aren't included." under the per-child note. Days off that span the start are counted by their start day, as ticketed (not included).
- **S7-10 approach.** The engine returns the marker: `forecastOutcome` gives `{ finish }`, `{ beyondLimit: true }` (the loop ran out of its 730 days) or null (nothing to forecast); `forecastFinish` is kept as a wrapper with its old date-or-null answer, so its callers and tests are unchanged. `briefingLines` uses `forecastOutcome` and gives `beyondLimit` the same plain line as a forecast over 26 weeks late. The 730-day limit is unchanged. The test case is a 100-page book with check-ins of 0.1 and 0.2 pages (the tester's 44.4/44.6 depends on dates not recorded in the finding; the same shape: positive progress too small to finish).
- **S7-11 effective days.** `effectiveWeekdays` already resolved own, then the subject's default, so null versus an explicit list equal to the subject's days was already one thing. What was missing is the last step: with neither set, null means every school day, so null versus an explicit list equal to the family's school days stored a history record. `weekdaysChange` now reads null as the family's school days (when the caller passes them; the PATCH route does) for both the "nothing changed" test and the S4b-02 "changed back" test. What is stored as `previous_weekdays` is unchanged (the unresolved days before, null = every school day).
- **S7-12 the setting.** An environment variable (`TAP_WIDTH`), like the script's other settings; default 360. A value that is not a whole number from 280 to 1600 stops the script with a message instead of measuring a nonsense width. The script logs "Viewport width: N px" first. The flow's first `setViewport` (360) is overridden by the scenario's. Not run against a browser in this pass (needs the servers and Chromium); `node --check` passes.
- **S7-15 the fix.** Below 360 px the Start and End fields stack (Start over End, each filling the row, labels in a fixed-width first column so the two fields line up); 360 and up keep the S6b-05 side-by-side row untouched. Chose stacking over shrinking the gap: a native date input has a minimum width of about 125 px, which two of them plus labels cannot get inside 288 px. Checked in Chromium on the demo family with the bar open: at 320 px both fields are 44 px high and end at 308 px (inside the 320 px screen, page scroll width 320); at 360 px they sit side by side as before (52 to 177 and 212 to 344). The ticket's tests are the tester's browser pass, so no jsdom test (jsdom has no layout).
