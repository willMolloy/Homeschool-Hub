- **S14-01 `session.parent_id` is nullable.** Sign-in always sets it; about twenty older API tests insert a session with only a family id, and those keep working (the family still comes from the session; such a session has no parent name). The composite foreign key still stops a session naming a parent of another family.
- **S14-01 a parent's name for existing logins** is the part of the email before the @ (the old login had no name), "Parent" if empty. There is no screen to change it yet.
- **S14-01 the old columns are dropped, not kept,** in the same migration, as the ticket allows once the migration test verifies the move.
- **S14-01 password reset CLI** requires the parent to exist (it never creates one); `set-family-login` is the creating alias.
- **S14-02 a taken email is told so** ("That email is already used for a sign-in. Try a different one.", 409). Someone holding a valid link could therefore learn that an email has an account. The link is a secret, redeeming is throttled and the alternative (a silent failure) strands a real parent, so this is the smaller harm.
- **S14-02 a new family is named "Our family"** until the setup flow's first step asks (it is already prefilled with the family's name).
- **S14-02 `list` shows no links.** Only a hash is stored, so a lost link means making another (and `revoke` for the old one).
- **S14-02 the page checks the link when it opens** (`GET /api/join/:token`) so a dead link shows its message before anyone types; the throttle counts these looks.
- **S14-03 the link is shown once, in the page's memory only.** After the page is left, the open-invite list can only say that an invite exists; to share it again, cancel it and make a new one. (Only a hash is stored, so the alternative would be storing the token.)
- **S14-03 at most five open invites per family** (not in the ticket): a small safe cap so the list and the table can't be filled by mistake or by a stuck button.
- **S14-03 parents are listed by name only** (no emails), as the ticket says.
- **S14-03 the demo family can't invite** (it is for looking around; same rule as events).
- **S14-04 the hourly sliding step stays** (a used session is renewed at most once an hour): a session is therefore valid for at least 29 days 23 hours after its last use, and at most 30 days. Renewing on every request would write to the database on every call.
- **S14-04 the sweep also runs at start and hourly,** not only at sign-in, so a quiet server still tidies up.
- **S14-05 the CSV row cap goes from 50 to 200** (not in the ticket, which says "a 60-row CSV"): the import already validates every row before sending anything, so a bigger file costs nothing extra, and the chunks are the copy panels' tested path. 200 is the smallest round number that is comfortably past one chunk of 50.
- **S14-05 the refusal checks are on the shared undo step,** so a copy (S7b-11) is refused after a completion answer or a log entry as well. The ticket names only the bulk panels; one rule for all three is safer and simpler. In practice `log_entry` is the old per-assignment log table the app no longer writes, and a completion answer made through the app also replaces the undo entry (it is a plan change), so these two checks are a backstop.
- **S14-05 week adjustments do not block an undo:** they go with the assignment when it is deleted, and an adjustment is itself a plan change that replaces the undo entry.
